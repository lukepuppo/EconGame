# Blackjack Hi-Lo simulator (C++ vs Rust)

Simulates 100,000,000 rounds of 6-deck blackjack played with perfect Hi-Lo advantage play in
**about 0.40 s (C++) and 0.44 s (Rust) on a 4-core cloud VM**, with every run under 0.5 s. That's
about 230-250M rounds per second, roughly 23× the first version. C++ and Rust each have two engines: an AVX-512 "lockstep" engine
that plays 16 games per vector instruction, and a scalar reference engine. All four produce
byte-identical results for the same seed.

```
./compare.sh [rounds=100000000] [threads=nproc] [seed=1]  # build, check C++ == Rust == reference, time
make -C cpp test                 # C++ suite (AddressSanitizer + UBSan)
(cd rust && cargo test --release)
make -C cpp perf                 # performance test: all 10 runs of 100M rounds must be < 0.5 s
./perf_test.sh ./rust/target/release/bj 0.5
./bench.sh 9 binA binB           # compare builds fairly on a noisy machine (min and median)
./cpp/bj 100000000 4 1 basic     # flat-bet basic strategy baseline
./cpp/bj 100000000 4 1 hilo ref  # same run on the scalar reference engine
```

Needs an AVX-512 CPU for the fast engine (Intel Skylake-SP or later, AMD Zen 4 or later).
Elsewhere both programs fall back to the scalar engine automatically.

## Rules
6 decks, reshuffle after 5 decks dealt (83% penetration). Dealer stands on soft 17 and peeks for
blackjack. 3:2 blackjack. Double on any two cards, double after split. Split up to 4 hands; split
aces get one card each and can't be resplit. Late surrender. Insurance is offered.

## Player
- **Basic strategy:** 4+ deck S17/DAS/LS chart.
- **Hi-Lo count:** 2–6 = +1, 7–9 = 0, T/A = −1. The dealer's hole card is counted when it's turned
  over. True count = running count ÷ unseen decks, compared exactly with integers (no rounding).
- **Deviations:** Illustrious 18 (Schlesinger), including insurance at TC ≥ +3, plus the Fab 4
  surrenders (14v10 +3, 15v10 0, 15v9 +2, 15vA +1).
- **Bet ramp:** 1-12 units on the floored true count: ≤+1 → 1, +2 → 2, +3 → 4, +4 → 6, +5 → 8,
  +6 → 10, ≥+7 → 12.

## Results: 100,000,000 rounds, seed 1

| | Hi-Lo + I18/Fab 4, 1-12 spread | Basic strategy, flat bet |
|---|---|---|
| Player edge (vs initial bet) | **+1.159% ± 0.035%** | −0.350% ± 0.022% |
| Edge vs total action | +1.005% | −0.309% |
| Flat-bet edge (same play, 1 unit every round) | −0.226% | −0.350% |

The deviations alone are worth about 0.12%; the bet spread is what turns the game positive. The
basic-strategy figure matches the published house edge for these rules (about 0.35–0.40%).

## Performance

100M rounds, 4-core Sapphire Rapids VM. "Before" is the first version of this simulator.

| | 1 thread | 4 threads, 100M rounds |
|---|---|---|
| First version (scalar, if-chain strategy) | 11 M rounds/s | 2.28 s |
| Scalar + strategy matrix (today's `ref` engine) | 14 M rounds/s | ~1.8 s |
| **AVX-512 lockstep engine, C++ (clang 18)** | **65 M rounds/s** | **0.39–0.48 s** (typically ~0.40) |
| **AVX-512 lockstep engine, Rust 1.97** | **57 M rounds/s** | **0.42–0.49 s** (typically ~0.44) |

The 4-thread ranges are 10 consecutive runs each. Times on this VM vary by about ±10% from run
to run, so use `bench.sh` to compare builds. C++ is
built with clang because GCC 13 was ~10% slower on the vector engine.

### How it gets there, and where the ideas come from

1. **Lockstep SIMD across independent games (predication).** Each 32-bit lane of a 512-bit
   register is a separate game with its own shoe. Branches become lane masks, the way GPUs run
   divergent threads and the way
   [AVX-512 masked instructions](https://LLVM.org/devmtg/2015-04/slides/MaskedIntrinsics.pdf)
   vectorize divergent control flow. The hit and dealer loops run until no lane still draws.
   - **Rare-path fallback.** The vector path plays a split as two hands. A lane that would split a
     *second* time (~0.3% of rounds) is rewound to the start of the round and replayed by the
     scalar engine.
2. **Strategy matrix as a gather.** Each decision is one gather from a
   `[hand class][upcard][rule flags]` table holding `{basic play, deviation, index}`, then one
   exact true-count compare. The table is generated by probing the readable `decide()` function,
   so the two can't drift apart.
3. **Pre-shuffled shoes and batched bounded random numbers.** A reshuffle runs Fisher-Yates up
   front, so dealing is an array read.
   - All swap targets are computed before any swaps, 16 at a time with one vector multiply. This
     uses Lemire's
     [nearly divisionless bounded integers](https://arxiv.org/abs/1805.10941v4) and the idea from
     Brackett-Rozinsky & Lemire,
     [*Batched Ranged Random Integer Generation*](https://arxiv.org/abs/2408.06213v1) (2024, also
     adopted by Go), of never spending a 64-bit draw on a value below 2⁹.
   - Blocks that might hit the rejection zone (~10⁻⁶) take an exact scalar path.
4. **Multi-stream SIMD xoshiro256++.** Each shoe's RNG runs 8 independent
   [xoshiro256++](https://simdrng.readthedocs.io/en/latest/guides/xoshiro.html) streams side by
   side, as in [VectorizedRNG.jl](https://github.com/JuliaSIMD/VectorizedRNG.jl) and
   [simd-rand](https://github.com/ashayp22/simd-rand). A single stream is a serial chain at ~5
   cycles per step. The ++ scrambler avoids 64-bit vector multiplies (`vpmullq`, ~15-cycle
   latency on Intel).
5. **Hit rule without lookups.** For hands of three or more cards the only choices are hit and
   stand. The strategy matrix reduces to "stand iff value ≥ S(upcard)", where S drops by one at up
   to two true-count breakpoints, and the builder asserts this shape. Each breakpoint test
   `tc ≥ b` is kept as `rc·52 − b·unseen ≥ 0` and updated with two adds per card. That takes a
   table gather and two 10-cycle multiplies off every hit decision (~4%).
6. **Card window.** The 8 cards after the deal are gathered alongside it, so later draws are
   register byte-shifts (~3 cycles) instead of dependent gathers (~20+).
7. **Interleaving independent groups.** The round is latency-bound, so three 16-lane groups
   advance phase by phase in turn and their dependency chains overlap (software pipelining).
   One group gives 52M rounds/s on one thread; three give 62M.
8. **Packed histogram.** Each lane's true-count histogram cell holds the round count in its high
   bits and the flat-net sum in its low 19 bits, so one gather+scatter updates both (~3%).
9. **Deterministic dynamic scheduling.** The work is 128 lane sets with fixed seeds and round
   counts, handed out to threads from an atomic counter, so one slow core doesn't hold up the
   run. Output is the same for any thread count.

### Profile and what didn't work

Found by measuring each component's cost on its own. On one thread, shuffling is ~40% of the
time and the vector round ~60%.

| Tried | Result |
|---|---|
| Vectorized shoe generation (16 shoes at once, sequential sampling from rank counts) | Same cost as Fisher-Yates (~1.1 ns/card), more complex |
| Shuffling in the background between vector phases | Slower: the swaps compete with gathers for load ports |
| Interleaving two shoes' Fisher-Yates swaps | Slower: the swap loop is load/store-port bound (~1.8 cycles/card) |
| Shuffling only dealt cards (lazy tail) | Slower: the extra branch in the hot draw path costs more than the saved swaps |
| Building the shuffle's swap targets straight from registers | No measurable change |
| Event counters as scalar popcounts | Slower |
| Branch-free first loop iterations | No change |
| GCC profile-guided optimization | ~3% gain, within noise |

## Test suite

The C++ suite runs under AddressSanitizer + UBSan; both languages run the same checks.

| Test | What it guards |
|---|---|
| Vector engine ≡ scalar reference, lane by lane (stats, shoe, count, RNG state; 1 and 3 groups; both modes; scalar tails; repeated runs) | Every engine rule |
| Vectorized shuffle ≡ textbook Fisher-Yates, from misaligned RNG positions and with forced rejections | The shuffle fast path |
| SIMD RNG refill ≡ scalar xoshiro256++ | The RNG |
| Lane seeds never repeat across lane sets | Independence of games |
| Chi-square uniformity of ranks at several positions; shoe composition and Hi-Lo balance | Shuffle quality |
| Every Illustrious 18 / Fab 4 index at its threshold; basic strategy spot checks; strategy matrix ≡ `decide()` | Strategy |
| Running count ≡ cards dealt; basic-strategy and Hi-Lo edges within the published range | End-to-end sanity |
| `perf_test.sh`: 100M rounds, 10 runs, every one under 0.5 s | The speed goal |

Bugs these tests caught while building the vector engine:
- An aligned 256-bit store to an unaligned address, after a rare scalar step in the shuffle. Only
  ASan saw it; optimized builds happened to work.
- A true count computed from a stale card count during multi-card hands.
- A split lane winning both hands but counted as one win.
- An unused spare shoe consuming RNG output.
- **Lane-set seeds that overlapped**, so most of the "independent" games were replays. The
  engines all agreed with each other, but the Hi-Lo edge read 0.92% instead of 1.16%.

Re-injecting the first and third bugs makes the suite fail.

## Memory
- **Per game:** a lane is 1.5 KB: a 312-byte shoe, its 8-stream RNG with a 64-word buffer, the
  count and the stats. The hot loop never allocates.
- **Shared:** the strategy matrix is 15 KB, one copy shared read-only by all threads.
- **Money:** amounts are kept in half-units, so 3:2 payouts, insurance and surrender stay exact
  integers.
